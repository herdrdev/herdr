Shepherd detects the agents it supports automatically. Install an agent's integration so Shepherd can resume the same session after a server restart. Some integrations also report the agent's state directly. See [Agents](/docs/agents/) for which agents Shepherd supports and which support Shepherd themselves.

## Install integrations

Open settings inside Shepherd and use the integrations tab to install recommended integrations for agents found on your `PATH`, or run commands manually:

```bash
shepherd integration install pi
shepherd integration install omp
shepherd integration install claude
shepherd integration install codex
shepherd integration install copilot
shepherd integration install devin
shepherd integration install droid
shepherd integration install kimi
shepherd integration install opencode
shepherd integration install kilo
shepherd integration install hermes
shepherd integration install qodercli
shepherd integration install qwen
shepherd integration install letta
shepherd integration install cursor
shepherd integration install mastracode
shepherd integration install antigravity-cli
shepherd integration install grok
```

```bash
shepherd integration uninstall qwen
shepherd integration uninstall letta
shepherd integration uninstall cursor
shepherd integration uninstall mastracode
shepherd integration uninstall antigravity-cli
shepherd integration uninstall grok
```

Shepherd saves integration configs atomically on Linux/macOS and for new files; existing Windows files keep their permissions through a backup-first, in-place update. If Windows reports a backup, close the agent and inspect the config before retrying: discard—not restore—an unfinished `.shepherd-backup.pending` only after verifying the config, or restore completed `.shepherd-backup` contents into the existing file if needed (if missing, establish its intended permissions first), then verify the config and remove the backup.

## How Shepherd uses integrations

Every integration tells Shepherd which session the agent is in, so Shepherd can resume it after a server restart. Turn this off with `[session] resume_agents_on_restore = false`.

The Pi, OMP, Kimi Code CLI, OpenCode, Kilo Code CLI, and MastraCode integrations also report the agent's state. While they report, Shepherd uses them instead of reading the screen. The others leave state to screen detection.

Native session restore requires current Shepherd integrations: Pi integration version `2`, OMP version `3`, Claude Code version `6`, Codex version `5`, GitHub Copilot CLI version `2`, Devin CLI version `2`, Droid version `2`, Kimi Code CLI version `3`, Qoder CLI version `2`, Qwen Code version `1`, Letta Code version `1`, Cursor Agent CLI version `1`, Grok CLI version `2`, OpenCode version `5`, Kilo Code CLI version `1`, Hermes Agent version `5`, MastraCode version `1`, or Antigravity CLI version `1`. Check installed versions with `shepherd integration status`.

## Integrate your own agent

If you build a coding agent, you can report its state and resume command to Shepherd from your own code, without adding native support to Shepherd. See [Add Shepherd support to your agent](/docs/add-shepherd-support/).

## Pi

Install the Pi integration:

```bash
shepherd integration install pi
```

Shepherd writes the bundled extension to:

```text
~/.pi/agent/extensions/shepherd-agent-state.ts
```

If `PI_CODING_AGENT_DIR` is set, Shepherd writes to `$PI_CODING_AGENT_DIR/extensions/shepherd-agent-state.ts` instead. Shepherd creates the extensions directory when the Pi agent directory already exists. Uninstall removes only that extension file.

## OMP

Install the OMP integration:

```bash
shepherd integration install omp
```

Shepherd writes the bundled extension to:

```text
~/.omp/agent/extensions/shepherd-omp-agent-state.ts
```

Shepherd uses `PI_CODING_AGENT_DIR` as the complete agent directory when set. Otherwise, it uses `$HOME/$PI_CONFIG_DIR/agent` when `PI_CONFIG_DIR` is set, falling back to `~/.omp/agent`. If Pi and OMP resolve to the same extension directory, Shepherd refuses the OMP install so the OMP extension cannot be loaded by Pi. Configure separate agent directories before installing both integrations. Shepherd creates the extensions directory when the resolved OMP agent directory already exists. Uninstall removes only that extension file.

The OMP integration reports `omp` as the agent label, lifecycle state, and native session identity through Shepherd's socket API. It does not require native process detection for the `omp` executable, and Shepherd can resume an OMP pane with `omp --resume=<session>` after a server restart.

## Claude Code

Install the Claude Code hook:

```bash
shepherd integration install claude
```

The hook reports Claude Code session identity to the local Shepherd socket on session start. Claude Code state comes from Shepherd's screen manifest detection.

Claude integration v10 matches only the documented `SessionStart` sources: `startup`, `resume`, `clear`, `compact`, and `fork`. This prevents Grok's `new` and `load` events from launching the imported Shepherd Claude hook, without disabling unrelated Claude-compatible hooks. Reinstall the Claude integration after upgrading to migrate the previous wildcard matcher. New Claude source values require an integration update.

Shepherd uses `~/.claude` by default, or `CLAUDE_CONFIG_DIR` when set. The Claude config directory must already exist. Install writes `hooks/shepherd-agent-state.sh` and updates `settings.json` with Shepherd hook entries. Uninstall removes the matching hook entries and deletes the hook script.

## Codex

Install the Codex hook:

```bash
shepherd integration install codex
```

The Codex hook reports session identity through the same local socket API used by other integrations. Codex state comes from Shepherd's screen manifest detection.

Shepherd uses `~/.codex` by default, or `CODEX_HOME` when set. The Codex config directory must already exist. Install writes `shepherd-agent-state.sh`, updates `hooks.json`, and ensures `[features] hooks = true` in `config.toml`. It also removes the deprecated top-level `codex_hooks` flag when present. Uninstall removes Shepherd entries from `hooks.json` and deletes the hook script, but leaves `config.toml` unchanged.

## Devin CLI

Install the Devin CLI hook:

```bash
shepherd integration install devin
```

The hook reports native session identity from Devin session, prompt, tool-use, permission, and stop events. Devin state still comes from Shepherd's screen manifest and OSC detection because Devin hooks do not emit a reliable state transition after every permission cancellation or user interrupt.

Shepherd uses `$XDG_CONFIG_HOME/devin` when `XDG_CONFIG_HOME` is set. Otherwise, it uses `~/.config/devin` on Linux and macOS or `%APPDATA%\devin` on Windows. The Devin config directory must already exist. Install writes `shepherd-agent-state.sh` on Unix or `shepherd-agent-state.ps1` on Windows and updates `config.json` with Shepherd hook entries. The hook refreshes the session reference while Devin runs. Uninstall removes Shepherd entries from `config.json` and deletes the hook script.

Shepherd resumes stored Devin sessions with `devin --resume <id>`. Native screen manifest detection remains the state authority whether or not the hook is installed.

## Kimi Code CLI

Shepherd resumes stored Kimi sessions with `kimi --session <id>`.

## OpenCode

Install the OpenCode plugin:

```bash
shepherd integration install opencode
```

The integration supports OpenCode V1 `1.18.29` or later and OpenCode V2 (tested with beta `19242`). The OpenCode config directory must already exist. Shepherd installs the server entrypoint at `~/.config/opencode/plugins/shepherd-agent-state.js`, the shared TUI plugin at `shepherd-tui-session.js`, and a V2 TUI entrypoint at `shepherd-opencode/tui.js` in that config directory.

Install registers the V1 TUI plugin in `tui.jsonc` and the V2 TUI plugin in `cli.json`, preserving other preferences and plugins. An existing V1 registration in `tui.json` also counts as installed and is reused without creating `tui.jsonc`. Uninstall removes the Shepherd registration from both TUI config files while keeping the files and other preferences. If OpenCode still has V1 TUI preferences to import (`tui.json` or `kv.json`), Shepherd defers registration so the first-start migration can run; start `opencode2` once and reinstall the integration afterward. Otherwise Shepherd creates `cli.json` with the plugin registration. Restart the OpenCode TUI after installation. Uninstall removes the managed plugin files and their configuration entries.

V2 lifecycle reporting runs in the pane-local TUI, which associates events with its selected root session even when multiple panes share one OpenCode server. Completion and interruption clear the working state; pending permission requests, pending forms, and failed executions keep the pane blocked. V2 Mini and headless clients do not run the TUI plugin and therefore do not provide this lifecycle reporting.

V1 TUI reporting follows the pane's selected session and its descendants. The pane stays working while any of them is busy or retrying, and blocked while any has a pending permission or question. Attaching loads existing activity; cancelled tool requests do not become blockers again after reconnecting. Browsing a subagent keeps the original session family, while directly attaching to a child tracks that child's subtree rather than its siblings.

Local V1 `opencode run` and `opencode --mini` retain their legacy server hooks; this change does not add pane-local lifecycle reporting to Mini/headless clients. After updating the integration, restart shared OpenCode servers as well as their TUIs so the old server reporter cannot overwrite pane-local state.

The plugin reports lifecycle state and session identity while OpenCode runs inside a Shepherd pane. After OpenCode emits a session-bearing event, Shepherd can use the reported session id to resume the pane with `opencode --session <id>`. Native screen manifest detection remains available when the plugin is not installed.

## Hermes Agent

Install the Hermes Agent plugin:

```bash
shepherd integration install hermes
```

Shepherd writes `plugins/shepherd-agent-state/` under the Hermes home directory and enables `shepherd-agent-state` in its `config.yaml`. `HERMES_HOME` defaults to `~/.hermes` on Unix and `%LOCALAPPDATA%\hermes` on Windows. The Hermes config directory must already exist. Restart Hermes after installing so the plugin loads. Uninstall removes the plugin directory and removes `shepherd-agent-state` from `plugins.enabled`.

The plugin reports the resumable session id while Hermes runs inside a Shepherd pane. Shepherd uses screen manifest detection for `working`, `idle`, and `blocked`, and can use the reported session id to resume the pane with `hermes --resume <id>`.

## Letta Code

Letta Code integration installation is experimental and CLI-only. It is not listed in the Settings integration screen or the JSON integration API. `shepherd integration status` reports it as `letta (experimental)`. Agent detection and `shepherd agent start --kind letta` are supported independently of this installation restriction.

Install the Letta Code hook:

```bash
shepherd integration install letta
```

The quiet `SessionStart` hook reports the conversation ID for native restore. Letta Code state still comes from Shepherd's screen manifest detection.

Shepherd uses `~/.letta`. The config directory must already exist. Install writes `hooks/shepherd-agent-session.sh` (`hooks/shepherd-agent-session.ps1` on Windows) and adds a Shepherd entry to `settings.json`. Uninstall removes only the matching entry and managed script.

Shepherd resumes named conversations with `letta --conversation <id>`. It records the default conversation as `default:<agent-id>` and resumes it with `letta --conversation default --agent <agent-id>`.

## Antigravity CLI

Install the Antigravity CLI hook:

```bash
shepherd integration install antigravity-cli
```

Shepherd uses `~/.gemini/config/` by default, or `ANTIGRAVITY_CLI_CONFIG_DIR` when set. This is the directory Antigravity CLI reads global customizations from, and it must already exist. Install writes `hooks/shepherd-agent-state.sh` (or `shepherd-agent-state.ps1` on Windows) and adds a Shepherd-owned `shepherd` block to `hooks.json`. Antigravity CLI keys `hooks.json` by hook name, so install rewrites only that block and leaves other named hooks untouched. Uninstall removes the `shepherd` block and deletes the hook script.

This session-only integration reports the pane's current conversation, but not agent state. Shepherd keeps deriving working, idle, and blocked from what Antigravity CLI draws on screen.

The hook runs on `PreInvocation`, so Shepherd learns the conversation once the first prompt is sent. From then on Shepherd can resume the pane with `agy --conversation <id>` after a Shepherd server restart.

## Grok CLI

Install the Grok CLI hook:

```bash
shepherd integration install grok
```

The hook reports session identity through Grok's `SessionStart` hook while Grok CLI runs inside a Shepherd pane. Grok state comes from Shepherd's screen manifest detection.

Shepherd uses `~/.grok` by default, or `GROK_HOME` when set. The Grok config directory must already exist. Grok merges every `hooks/*.json` file in that directory, so install writes a self-contained `hooks/shepherd.json` with the Shepherd `SessionStart` entry next to `hooks/shepherd-agent-state.sh` (`hooks/shepherd-agent-state.ps1` on Windows), and never edits other hook files. Uninstall removes exactly those two Shepherd-owned files.

After Grok emits a session start event, Shepherd can use the reported session id to resume the pane with `grok --resume <id>`.

## Custom status labels

Integrations report lifecycle state as semantic state only. For example, report an agent as `working` without adding display fields to the lifecycle report.

```bash
shepherd pane report-agent w1:p1 \
  --source custom:docs \
  --agent docs-bot \
  --state working
```

User hooks that run next to a Shepherd-managed integration should use metadata instead of `report-agent`. Metadata changes presentation without taking over the integration's `idle`, `working`, `blocked`, or session restore authority. `--agent` and `--applies-to-source` guard only presentation fields (`--title`, `--display-agent`, and `--state-label`). Token patches always apply; their reporter owns clearing or TTL refresh. `--display-agent` changes the visible name.

```bash
shepherd pane report-metadata "$SHEPHERD_PANE_ID" \
  --source user:claude-title \
  --agent claude \
  --title "Refactor auth middleware" \
  --display-agent "Claude: auth" \
  --token summary="refactor auth" \
  --state-label working="refactoring auth" \
  --ttl-ms 3600000
```

Tokens and state labels are visual-only. Waits, notifications, and workspace rollups still use the semantic state.

## Debug integration state

List known agents:

```bash
shepherd agent list
```

Read a pane when you need to verify what Shepherd can see:

```bash
shepherd pane read w1:p1 --source recent --lines 50
```

If integration state looks wrong, first confirm the agent is running inside Shepherd and that the relevant hook or plugin was installed for the same user account.
